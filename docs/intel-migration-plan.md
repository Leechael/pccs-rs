# Intel PCCS snapshot migration

Scope approved by Leechael: work from `origin/main`; implement an offline SQLite importer and targeted registration/refresh fixes. Leechael subsequently authorized committing, pushing this feature branch and opening a PR against `main` after verification. Production actions, snapshot operations, token rotation and cutover remain unauthorized.

## Interfaces and invariants

The confirmed seams are `pccs-rs db import-intel <snapshot.db> --db-path <fresh-directory>` and the existing HTTP registration/certificate/refresh interfaces. Tests use real SQLite and RocksDB; only Intel's HTTP boundary is mocked.

1. The SQLite source is never written, migrated, or opened by the server. Import performs no network requests.
2. Existing destinations are never overwritten. Invalid snapshots and failed writes never publish a usable partial destination.
3. Every platform retains its complete certificate pool and registration credentials. Decoding imported Manifest hex yields the original BLOB bytes.
4. Raw CPU/PCE SVN mappings retain their SQL-selected `tcbm`; they are not inferred from certificate TCBs or reselected during import.
5. TCB and identity response bodies retain their original UTF-8 BLOB bytes, including whitespace and JSON spelling. Issuer chains retain intermediate/signing-before-root URL-encoded PEM form.
6. A successful Manifest-only registration returns success, stores the pool, and permits a subsequent PPID-less certificate GET. In REQ mode the successful registration leaves no NEW queue row.
7. Certificate refresh never exposes a new pool paired with selected responses from an incompatible old pool. Unavailable selections do not become untracked permanent cache hits. A stale in-flight fetch must not overwrite credentials from a concurrent successful registration.
8. Production startup does not discover or load development fixtures.

## Existing code and inventory

- Entry: `src/config.rs` clap commands; `src/main.rs` dispatch; `src/lib.rs` app construction; `src/routes/handlers.rs` validates and returns HTTP collateral.
- Storage: `src/store.rs` typed pool, selected PCK, TCB, identity, CRL, registration and policy records. Keys are generated by `src/keys.rs`, not handwritten readable paths.
- Actions: `src/cache.rs` GET local selection/fill, POST registration, explicit cert refresh, scheduled collateral-only refresh. `src/selection.rs` reads X.509 SGX extensions and little-endian PCE SVN.
- External adapter: `src/pcs.rs` Intel GET encrypted PPID / POST `{platformManifest,pceid}`; successful responses carry complete pools and encoded issuer chains.
- Existing imports: startup seeds ignore write errors, omit unselected pool certificates and reserialize signed documents; collateral PUT reselects mappings and is not an atomic snapshot restore. Neither is reused as the migration interface.
- Existing tests: `tests/api_1to1.rs` exercises HTTP, `src/cache.rs` mock-Intel tests exercise cache fill; no SQLite restore test exists.
- Consumers: QCNL expects `/pckcert` PEM, SGX-TCBm/FMSPC/CA/encoded-chain headers; dstack and dcap-qvl expect SGX/TDX signed TCB/identity JSON and CRLs; admin clients use POST registration, explicit refresh, draining GET registration queues and policy GETs. No consumer reads Intel SQLite through Rust.

## Source data and evidence boundary

The live instance is reported as Intel PCCS 1.24, db_version=5/api_version=4: 137 platforms, 1014 pool certs, 188 raw mappings, 45 TCB documents, 10 identities, 4 CA/signing certificates, 2 chain records, 2 PCK CRLs. Exactly one platform has a 17950-byte Manifest and no encrypted PPID. These counts and identity labels are NOT executable production fixtures.

Schema reference: Intel `DCAP_1.24`, commit `061143e22c7cc9049194f1b9b86e50ef4bc5ae75`, service migrations 00–05 and DAO models. Live `sqlite_master` and type/length/key/pointer statistics were received read-only at 2026-10-14T22:03:57Z. The 13-table DDL is represented without production rows in `tests/fixtures/intel-v5-live-schema.sql`; it confirms two legacy SGX v3 TCB records, four v3 identity variants, correct issuer pointers and zero missing platform/certificate joins. A protected full snapshot is still pending. Payload tests use explicitly synthetic executable BLOBs, certificates, mappings, chains and signed-document shapes. Synthetic certificates/signatures test transport fidelity and selection, not cryptographic trust of production evidence.

Intel's [PCS v4 API documentation](https://api.portal.trustedservices.intel.com/content/documentation.html) defines `tcbm` as the hex-encoded concatenation of CPUSVN and PCESVN **from the corresponding certificate**, not the original raw request. PCE SVN is encoded little-endian. The importer checks this certificate/TCBm relationship while preserving the separate SQL raw→TCBm mapping; nonuniform-CPU/asymmetric-PCE tests catch byte-order errors. Actual production certificates and legacy identity bodies still require the protected-snapshot rehearsal.

Required shapes: binary Manifest/encrypted PPID; PEM leaf BLOB; raw SVN text (PCE SVN little-endian); signed UTF-8 JSON BLOB; numeric SGX/TDX/id/API discriminators; encoded certificate-chain BLOB; DER CRL BLOB; queue states 0/1/9; appraisal type 0/1/2 and stored defaults. Missing joins, unknown variants, malformed blobs and legacy NULL types must be errors, not silently relabeled rows. Diagnostics must not dump credentials or complete payloads.

## State and order

| State | Trigger | Source | Next state | Invariant |
|---|---|---|---|---|
| source snapshot | validate/read | import operator | validated records | source unchanged, no network (1) |
| source snapshot | invalid schema/join/body | import operator | rejected | no destination (2) |
| validated records | persist to private staging | importer | staged store | all logical records retained (3–5) |
| staged store | close/reopen/readback | importer | verified store | count and byte fidelity (3–5) |
| verified store | exclusive destination publication | importer | published store | no overwrite/partial publish (2) |
| existing destination | any import | import operator | rejected | destination unchanged (2) |
| unknown indirect platform | successful POST | registration client | cached platform | successful response + PPID-less GET (6) |
| cached platform | successful cert refresh | admin HTTP | refreshed platform | pool and GET entries agree (7) |
| cached platform | failed upstream/selection | admin HTTP | retained old state or safe miss | no mixed/stale successful response (7) |

Time axis: T0 immutable SQLite snapshot → T1 validate/stage → T2 reopen and compare → T3 publish → T4 start offline server/read collateral → T5 restart/read again. Failure/retry at T1/T2 leaves source unchanged and destination absent; retries against T3 destination reject rather than merge. Snapshot→cutover source deltas are operator reconciliation, not incremental importer behavior.

## Vertical trace and coverage plan

```
SQLite snapshot → read-only transaction → strict schema/row/join validation
              → typed pools + exact SQL GET mappings + raw signed records
              → fresh private RocksDB staging → reopen/readback → publish
HTTP POST → validation → Intel manifest POST → pool fill → 200 → GET PEM
HTTP refresh → Intel cert pool + TCB selection → atomic pool/GET replacement
```

Intent labels: migration-safety for import/reopen/HTTP equality; regression for registration/PPID/refresh fixes; invariant for invalid imports/no source mutation/no overwrite.

| Seam | Success assertion | Failure/edge assertion |
|---|---|---|
| importer CLI | pool + raw GET + original bodies/chains/CRLs survive restart | no source change, no destination on missing join/invalid schema/body |
| pool migration | unselected certs and indirect credentials preserved | raw SVN intentionally differs from certificate `tcbm`; cannot infer mapping |
| discriminators | SGX/TDX, versions and updates remain distinct | unknown/NULL values rejected explicitly |
| metadata/queue/policies | complete row accounting, queue states/defaults/types retained | unknown nonempty table or invalid state fails |
| registration HTTP | Manifest-only POST succeeds; PPID-less GET matches | upstream error remains non-success; REQ success clears queue |
| PCK GET parity | known platforms use cached mappings/local selection regardless of omitted/full-length PPID | local selection failure never refetches with saved credentials; explicit empty PPID is invalid; unknown zero PPID fails; v3 remains no-network |
| cert refresh HTTP | changed selection is served after refresh | failed selection cannot serve stale old GET against new pool |
| startup | production fixture discovery disabled | explicit missing seed fails rather than choosing another file |

Feedback loop proven on the current baseline: `cargo test --locked --lib lazy_pckcert_with_manifest_fills_via_pckcerts_post` ran and passed (1 passed, 130 filtered, 2026-10-14). It is red-capable if manifest-only GET fill stops posting/fails to preserve the pool; assertion target is returned cert/metadata. The registration/refresh/parity regressions were demonstrated RED→GREEN before their corresponding fixes. Schema-only characterization and persisted-metadata assertions extend coverage without claiming reproduction of a production incident.

Owner-directed PPID policy: match Intel PCCS 1.24 (`service/services/pckcertService.js:101–139` and `service/controllers/pckcertController.js:64–67`). A known platform uses only cached mappings/local selection; failure does not trigger a stored-credential lazy refill. Omitted or full-length zero PPID does not prevent valid known-platform selection. A supplied empty PPID is invalid. Only unknown-platform LAZY requests fetch using caller-provided credentials; saved Manifest/PPID remain available to authenticated registration and explicit refresh. This supersedes the initially explored automatic known-platform refill.

Coverage status: all-dimensions-covered = no. Production snapshot, actual QCNL/dstack/dcap-qvl verification, live cryptographic validation and cutover rehearsal remain pending; synthetic tests cannot substitute for them.

## Not in scope

- Changing indirect registration to direct: irreversible and unnecessary.
- Production restart/config/token reset or reverse-proxy reload: performed only by Leechael after acceptance.
- Incremental merge into a running destination: fresh imports are reproducible; final source deltas require a second snapshot/reconciliation.
- Migrating AMD/NVIDIA caches: not Intel SQLite data and not present on origin/main.

## Deployment acceptance

Use explicit persistent host storage, `--no-seed`, direct Intel upstream, a distinct loopback port and the existing API key. Protect snapshots and staging directories as registration credentials. Verify all source raw mappings plus usc5 without encrypted PPID, signed bodies, issuer chain fingerprints, CRL hashes, new-service restart and full verification consumers. Reconcile new indirect registrations before switching both public hostnames. Keep old container unchanged. Rollback after new indirect registrations requires replay/journaling or a registration hold; changing Caddy alone is insufficient.
